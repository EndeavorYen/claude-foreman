# 實例：mon-bakery 0.8.1（秤重照步驟分碗）

第一次實跑，2026-11-19。主模型 Fable，環境是雲端 session（固定開銷很高：一次什麼都不做的派遣 7.3 萬 token）。

## 任務

使用者回報：秤重畫面把整個部位的材料當成同一個碗累加，但材料其實分步驟加。定案：同一個步驟的材料算一碗。

## 計畫與結果

| 單元 | 模型 | 驗證 | 結果 |
|---|---|---|---|
| U1 核心函式 `bowls()` 與測試 | sonnet | 關卡 | 一次通過 |
| U2 盤點 20 道配方的 `uses`，加資料測試 | sonnet | 關卡＋驗證者（haiku） | 實作者回報沒問題；驗證者判 3 次不通過 |
| U4 步驟內分小碗（驗證後新增） | sonnet | 關卡 | 一次通過 |
| U3 秤重畫面與流程測試 | sonnet | 關卡 | 一次通過 |

成本行：

```
foreman：fable 規劃＋驗收｜claude-haiku-5-5 ×4（397k tok）、claude-sonnet-5-5 ×4（389k tok）
｜子代理合計 786k tok（其中固定開銷約 588k＝74k×8 次）｜重派 0｜關卡 1 擋下 0｜驗證者抓到 3｜交付 4、擱置 0
```

## 學到的事

- **驗證者值得。** 實作者盤點後回報「全部沒問題」。低一層的驗證者拿著攤平的資料逐道對照步驟文字，
  找到 7 道配方一個步驟用到多個容器，之後又找到「要先留一部分的材料不能累加」兩類。這些都是規格沒想到的情況。
- **給驗證者整理好的材料。** 用一支十行的腳本把每道配方的步驟和分碗結果印成一個檔，驗證者讀一次就能判。
  範圍小的複驗直接把內容寫進 prompt、不給工具，成本只比固定開銷多幾千 token。
- **工頭的規格錯了兩次。** 一次是憑印象寫「配方都在 recipes.ts」（實際有 13 道在 recipes2.ts），
  一次是要求「重複的材料只留第一次」，結果會讓後面步驟的畫面少顯示一樣材料。兩次都是實作者在
  `notDone`／`unsure` 講出來才發現。動筆前先 grep；回報的這兩欄一定要讀。
- **固定開銷是成本主體。** 8 次派遣裡 75% 的 token 是起跳價。這個任務在這個環境下，派工的 token 比主模型自己做還多；
  它買到的是獨立驗證抓到的問題，以及主線 context 沒有被 20 道配方的資料塞滿。
- **驗證者會一直找到東西。** 第 3、4 次的發現越來越細。工頭要判斷哪些是真的問題（修）、哪些是文字沒說清楚（列給使用者），
  不要為了讓它說 PASS 而無止境地改。
