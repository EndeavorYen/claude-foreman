# handoff：交接

長對話每一輪都重讀全部內容。段落結束後，舊內容對下一件事多半沒用，留著只是每輪付錢。
交接檔是明寫的、使用者看得到的，比自動壓縮可靠：他能檢查你留了什麼。

交接檔固定放在 repo 的 `.claude/handoff.md`，每次覆寫，不進版控（寫之前確認它被忽略：
`git check-ignore -q .claude/handoff.md || echo ".claude/handoff.md" >> .git/info/exclude`）。

## 寫交接檔

只寫**新 session 沒辦法從 repo 自己看出來的事**。程式長怎樣、規則是什麼，repo 和 CLAUDE.md 裡都有，不要抄。
寫之前先確認工作目錄的狀態（`git status`、最後一個 commit、有沒有推），照實寫。

```markdown
# 交接：<一句話說這段工作在做什麼>

寫於 <日期時間>，repo <名稱>，分支 <分支>，最後的 commit <短 sha 與訊息>（<已推／未推>）

## 現在的狀態
<做完了什麼、驗證到什麼程度。未提交的改動逐一列出檔案和用途。>

## 已經定案的事
<使用者做過的決定，每條附一句原因。這是最容易遺失、最不能重問的部分。>

## 下一步
<依序列出。每一步寫到「新 session 不用問就能動手」的程度：動哪個檔、要達到什麼。>

## 還沒決定、要問使用者的
<沒有就寫「無」。>

## 走過的冤枉路
<試過但行不通的做法和原因，免得新 session 重試。沒有就省略這一節。>

## 相關檔案
<路徑：一句話說它是什麼。只列下一步會用到的。>
```

寫完後：

1. 把檔案的重點用 3～5 行唸給使用者聽，尤其是「已經定案的事」，請他看有沒有漏。
2. 告訴他怎麼接：開新 session（或 `/clear`），第一句話說「接續」就好；新 session 開頭會自動被提示有交接檔。
3. 有未提交的改動時提醒他：交接檔記的是狀態，改動本身還在工作目錄裡，換 session 不會遺失，但換電腦會。

## 讀交接檔

新 session 開頭如果被提示有 `.claude/handoff.md`，且使用者要接續：

1. 讀它，再用 `git status` 和 `git log -1` 對一下現況。交接檔寫的 commit 和實際不同時，以實際為準，並告訴使用者哪裡對不上。
2. 用兩三行回報你理解的狀態和下一步，然後直接開始第一步，不要重問已經定案的事。
3. 這段工作做完後刪掉交接檔，免得下一個不相干的 session 被它誤導。

使用者開的是不相干的新任務時，不要讀它，也不要提它。

## 什麼時候主動建議

只在**段落結束**時建議：剛推上去、一個功能做完、使用者要換做不相干的事。這時如果對話已經很長，說一句
「這段做完了，要不要交接後開新的 session？」就好。任務進行到一半不要建議，1M 的 context 就是給這種時候用的。
