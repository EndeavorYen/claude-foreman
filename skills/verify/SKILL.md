# verify：獨立驗證

實作者（包括你）看自己的東西會覺得沒問題。沒參與的人拿著同一份材料逐條對，才看得到規格沒想到的情況。
這是整套裡唯一有實測證據的做法：第一次實跑，實作者回報「全部沒問題」之後，低一層的驗證者找到 3 類真的問題。

本檔所在資料夾記為 `<skill>`；帳本工具是同一個 plugin 的 `skills/foreman/scripts/foreman.py`，記為 `foreman`。

公式、規格、演算法的學理審查用使用者的 `blind-review` skill；這裡驗的是**做出來的東西**：程式改動、資料、產出。

## 流程

### 1. 寫下要驗什麼

列 2～5 條標準 C1…Cn。每條要能判 PASS 或 FAIL，並且是**設計規則**，不是實作細節。例：
「同一碗裡的材料，步驟文字都說是一起加的」，不要寫「`bowls()` 回傳正確」。

同時寫下**判斷尺度**：什麼算問題、什麼不算。沒有尺度的驗證者會把合理的情況也報成問題。

### 2. 把材料攤平成一個檔

不要讓驗證者自己翻 repo：它會花很多輪讀檔，還可能看漏。寫一支十行左右的腳本，把要驗的東西印成一個純文字檔，
一筆資料一段，把「輸入」和「結果」放在一起。例：每道配方的步驟文字，和秤重畫面最後分成哪幾碗。

改動是程式邏輯時，攤平的是「代表性輸入 → 實際輸出」的表，不是原始碼。範圍很小（一兩筆）就直接寫進 prompt。

### 3. 派驗證者

- 模型：比實作者低一層，最低 `haiku`；牽涉資料遺失、金額、權限的至少 `sonnet`。**`model` 一定要明寫。**
- 類型：有裝這個 plugin 就用 `foreman:verifier`（只讀、固定開銷小）。
- prompt 照 `<skill>/verify-prompt.md` 填。材料在檔案裡就要求「用一次 Read 讀完，不做別的工具呼叫」；
  材料寫在 prompt 裡就要求「不要使用任何工具」。

### 4. 判斷它找到的東西

驗證者的每個發現都要你判，分三種：

| 發現 | 處理 |
|---|---|
| 真的問題，改法明確，且跟使用者定案的原則一致 | 修。小而可逆的你直接修，最後列給使用者看 |
| 真的問題，但要選做法或取捨 | 停下來問使用者，不要替他決定 |
| 文字沒說清楚、它自己也標「無法判定」 | 不改。列給使用者，由實際在用的人決定 |
| 誤判（它誤解了資料或規則） | 不改。下次把尺度寫清楚 |

修完後**只複驗改過的部分**，把那幾筆直接寫進 prompt、不給工具。最多複驗兩輪：
驗證者會越找越細，兩輪後還有新發現，就把剩下的列給使用者，不要為了讓它說 PASS 一直改下去。

### 5. 記一筆

```
foreman verify-log --what "<驗了什麼>" --model <驗證者回報的模型 ID> --tokens <用量> --found <真的問題數> --fixed <你修的> --asked <留給使用者的>
```

`--found` 只算你判定為真的問題，誤判不算。這份紀錄用來回答「驗證值不值得繼續做」：
`foreman review` 會列出驗了幾次、幾次有抓到。使用者實際用過後發現的問題，用 `foreman feedback <v-編號> --issues <n>` 回填。

## 給使用者的回覆

- 驗證者抓到幾個、你修了哪些（每個一句）、哪些留給他決定。
- 驗證者標「無法判定」的，原樣列出。
- 一行成本：模型、token。
